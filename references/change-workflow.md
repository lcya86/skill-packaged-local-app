# 变更工序（上线之后怎么改）

定位：这是生命周期第 4 步——应用已交付，用户开始持续提新需求。目标：**改得快** 且 **不把 app 改坏**。

核心：防「改坏」靠**闸门**（冻结基线 + 双向对撞 + 断言只多不少），不靠小心。
一次改动 = 归一类变更 + 走六步工序 + 留一张变更单。

## 1. 变更 intake（不许跳过）

用户口头需求，动手前先压成三样，写进变更单：

| 项 | 要求 | 例 |
| --- | --- | --- |
| 一句话需求 | 用用户自己的话，不加解释 |
| 触发场景 | 他在什么操作 / 什么时点需要它 |
| 可观测结果 | 页面或命令里能看见什么变化 |

- **为什么**：需求不入档，半年后没人知道某个字段为什么长这样，也没人敢删。
- 判据：这三样缺一，就不算 intake 完成，不许进第 3 节工序。

## 2. 五类变更 × 风险与必跑验证

先归类（每次只归一类），再照表跑验证。

| 类 | 影响面 | 风险 | 先写 DESIGN？ | 必跑验证 |
| --- | --- | --- | --- | --- |
| ① 纯展示/文案 | `ui/*` | 最低 | 否 | 真机点一次 + 截图取证 |
| ② 新增字段/新键 | `lib/*` + 存储 | 低-中 | 否 | 缺键不导致整份校验失败；老数据读写一遍 |
| ③ 新增写操作/端点 | `lib/*` + `server.mjs` | 中-高 | 是 | 唯一写通道 + rev 乐观锁；写脏后还原 |
| ④ 改口径/改算法 | `lib/*` 核心 | **最高** | **是** | 新旧口径并存对账 |
| ⑤ 改前端结构/换壳 | `ui/*` 全量 | 中 | 是 | 不可回退项提前告知；真机全流程走一遍 |

分支要点：

- **② 新增字段**：老数据缺这个键是常态 → 校验逻辑必须「**缺键 = 默认值**」，不许整份 `state.json` 判无效。
  判据：拿一份**未含新键的旧备份帧**跑只读命令，不报错、不静默改值。
- **③ 新写操作**：写入只能走**唯一写通道**（`lib/` 或 `store.mjs`），端点不直接改 `state.json`；
  写前校验 `rev`、写后 `rev+1`（乐观锁）。判据：并发两个写请求，后到的应因 `rev` 不符被拒。
- **④ 改口径**：会改变**所有历史数字的含义** → 新旧口径**必须并存可对账**，不许原地替换。
  判据：对同一帧数据，旧口径与新口径各出一份，能逐项解释差值来源。

## 3. 六步安全改动工序

**① 冻结基线**

```bash
# 从备份帧挑“改代码前”的那一帧（别用当前 state，用户随时在改）
ls -lt <data_dir>/backups | head
# 或先跑一次只读命令落盘
node <app>/scripts/cli.mjs <只读子命令> > /tmp/baseline-$(date +%s).json
```

**② 改**：只改**唯一实现**（`lib/` 或 `store.mjs`）。新开关**默认等于旧行为**（不设变量 = 逐字段一致）。

**③ 双向对撞**：两个方向都要跑（第二向最容易漏）——

```bash
# 新代码 × 旧数据
# 旧代码 × 新数据      ← 最容易漏的一向
# 剔掉新增键后深度比对（jq / python），不只看断言数：
jq 'del(.新键)' out.json | diff - expected.json    # 形状示意，非写死脚本
```

**④ 断言只多不少**：跑零依赖测试，与**写在 SKILL.md 里的基线断言数**比对——新测试全过 + 老测试不回归。

**⑤ 登记**：变更单 + 补丁清单（若改了第三方包）+ 复发清单（若命中第 5 节）。

**⑥ 交付**：真机点一次；报告用「请求 → 返回」表，不给形容词。

| 请求 | 返回（期望） |
| --- | --- |
| `GET /api/health` | `{"ok":true,...}` |
| `POST /api/<新端点>` | `{"rev":<n+1>}` |

## 4. 变更单模板 `docs/CHANGES-<n>.md`

```md
# CHANGES-<n>  <一句话需求>

- 需求原话（用户语言）：
- 影响面（文件清单）：
- 变更类型：①/②/③/④/⑤
- 验证证据：命令 + 返回（贴原始输出，不转述）
- 回滚办法：数据走哪帧 / 代码走哪个 commit
- 遗留项：如实写没做的
```

- 判据：**回滚办法**、**遗留项**两栏必须填（没有就写“无”）；空着等于没写变更单。

## 5. 什么时候必须停下来重构

| 信号 | 动作 |
| --- | --- |
| 同一类缺陷**第 2 次**出现 | 停止打补丁 → 逻辑下沉到唯一实现 + 加断言钉死 |
| 同一字段被 **3 处以上**写入 | 收敛到唯一写通道 |
| 需求开始要求「两处口径不同」 | 停下来，先统一口径再动手 |
| 单文件超体量、每次改动都要碰它 | 拆分，或把稳定部分抽出去 |

- **复发次数是架构债的度量**。复发清单（哪一类 / 第几次 / 这次为什么又引入）放 **SKILL.md**，不放会话。
- 「第 2 次」是硬线：第 1 次可以打补丁，第 2 次必须改结构。

## 6. 回滚

| 对象 | 手段 | 备注 |
| --- | --- | --- |
| 数据 | `<data_dir>/backups/` 帧 + **CLI 还原** | 绝不手改 `state.json` |
| 代码 | git 回到改前 commit | 用变更单里记的 commit |
| UI | **不可回退 → 提前讲清** | 交付前告知用户 |

- 回滚本身也要写进变更单——回滚是变更的一种，不是例外。
- 还原后**再 diff 一次**确认；`rev` 会继续涨（写入已发生，属正常）。

## 7. 迭代节奏建议

- **小步快跑**：一次只做一类变更，每步独立可验收；别攒大改。
- **需求排队**：「顺手想到的」写进 backlog，不插进当前改动。
- **写回 SKILL.md**：每次改完把新口径/新约定写回 SKILL.md——**下个 Agent 读的是 skill，不是会话**。

## 8. 禁止清单

- 跳过 intake，直接动手改。
- 绕过 CLI 手改 `state.json`。
- 跳过冻结基线就改。
- 只跑单测就交付（没真机点、没对撞）。
- 改了 `scripts/*` 没重启就说改好了。
- 在没有备份帧的情况下动数据。
- ④ 类改动原地替换口径、不留旧口径对账。

## 9. 存疑项

- ②「缺键 = 默认值」在**深层嵌套对象**（对象在、子键缺）的边界未实测，按需在校验层单独钉。
- ④「新旧口径并存」的**并存时长**无硬标准；以“能解释完所有差值”为准。
