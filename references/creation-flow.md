# 创建链开局（需求 → 原型 → 出货）

原则：**先问后做，先原型后实现**。需求没被用户改过口，就别动正式代码；原型没被用户改过口，就别写后端。

## 1. C0 需求采集：苏格拉底式提问

目标是逼出**判据**而不是功能清单。三轮各问一次，每轮问完必须复述纠错（见 1.4）。

### 1.1 三轮框架

| 轮次 | 目标 | 拿不到的后果 |
| --- | --- | --- |
| 1 场景与判据 | 什么时候打开、看完做什么决定、现在怎么做、多久一次 | 做出来的页面没人用 |
| 2 数据血统 | 每个数字从哪来、谁录、多久变、错了怎么办、以谁为准 | 算法对、数据脏、结论全错 |
| 3 边界与非目标 | 绝对不要什么、给谁看、丢了怎么办、手机还是电脑 | 功能越加越多、隐私裸奔 |

### 1.2 第 1 轮 场景与判据（问句范本，可直接念）

- 「你一般在什么情况下会打开它——是每天固定看一眼，还是出了某件事才来查？」
- 「看完这个页面之后，你下一步要做什么决定？比如决定买还是卖、决定要不要提醒家里人。」
- 「这件事你现在是怎么做的——表格、纸、还是脑子记？」
- 「多久来一次——每天、每周，还是每月算账那两天？」

### 1.3 数据血统与边界（第 2、3 轮问句范本）

第 2 轮：

- 「页面上这个数从哪来？举个例子：这个成本价，是你手录的，还是从别处抄过来的？」
- 「谁来录它——只有你自己，还是家里还有人一起改？」
- 「这个数多久变一次——一天一变，还是基本不动？」
- 「如果录错了怎么办？你会怎么发现、怎么改回去？」
- 「两个地方说法不一样的时候，以哪一个为准？」

第 3 轮：

- 「有哪些东西是你绝对不要的？比如不要自动联网、不要推送、不要别人能登录。」
- 「这个东西给谁看——只有你，还是要给家人看？」
- 「如果数据丢了会怎样？是需要能恢复，还是无所谓重来？」
- 「主要在手机上用，还是电脑上？」

### 1.4 每轮结束必须复述纠错

把用户这一轮的话**压成一句可判对错的陈述**交回去让他改。模板：

> 「我理解的是：你会在<某种情况>下打开它，看完决定<某个动作>。对吗——哪里不对你直接说。」

- 复述要含**一个具体触发**和**一个具体产出**，否则用户只能回「差不多」。
- 用户改口 = 这一轮有效；用户说「对对对」= 还没问够，换角度再问。

### 1.5 追问范式（问不下去时换角度）

| 范式 | 一句话 | 能挖出什么 |
| --- | --- | --- |
| 删功能测试 | 「明天把这个功能删了，你会在哪一步卡住？」 | 真需求 vs 装饰 |
| 最坏情况 | 「最糟能糟到什么程度——错了会亏钱还是会尴尬？」 | 精度要求与告警必要 |
| 比较式 | 「A 和 B 哪个更常发生？」 | 优先级排序 |
| 怀疑链 | 「这个数错了，你会先怀疑哪一步？」 | 真实数据流向与信任点 |
| 反向确认 | 「如果它<做反了>，你会不会发现？多久发现？」 | 判据是否可观测 |

### 1.6 反模式（出现即停手重问）

1. 一次抛出 20 个问题——用户只会挑好答的答，判据永远问不出来。
2. 只问功能不问判据——「要有导出」不代表「导出给谁、导了干什么」。
3. 把用户提的方案当需求——「加个图」是方案，需求是「我想一眼看出这周是不是比上周差」。
4. 跳过「不做什么」——非目标不写下来，实现阶段就会自己长出来。
5. 不问谁维护——单人会用的东西，和家里两个人会改的东西，架构不同。
6. 不问数据来源就画界面——先有字段来源，才有字段。
7. 用户说了「随便」「都行」就当真——那是没想清楚，用比较式逼他二选一。

### 1.7 需求文档模板 `docs/REQUIREMENTS-<app>.md`

| 表 | 列 |
| --- | --- |
| 场景判据表 | 场景 \| 触发时机 \| 看完要做的决定 \| 现状做法 \| 频率 |
| 数据血统表 | 字段 \| 来源 \| 录入者 \| 变化频率 \| 错了怎么办 \| 权威源 |
| 边界与非目标表 | 类别 \| 内容（绝对不做 / 给谁看 / 数据丢失容忍度 / 设备） |
| 成功判据 | 一句话目标 \| 可观测信号（用户能指着一个画面说出「对了/不对」） |

判据必须**可观测**：能指着一个画面说出对错；说不出就是空判据，回去重问。

## 2. C1 原型先行

先交一个能点的假页面，用户改口之后才写正式版。原型是**证据**，不是草稿。

### 2.1 原型规格

| 项 | 要求 |
| --- | --- |
| 形态 | 单文件静态页（一个 `.html` 装下结构、样式、脚本） |
| 数据 | 真布局 + 假数据，字段与布局都按真实走 |
| 水印 | 显式 DEMO 标记，肉眼可辨，防被当成真实读数 |
| 交互 | 手机视口 390×844 下可点可输入，按键即响应 |
| 状态 | 只在内存，**不落库**，刷新即复位 |

### 2.2 移动端 H5 形态约定（并入本节，不另开文件）

| 项 | 约定 | 原因 |
| --- | --- | --- |
| 视口 | `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` | 不设则在手机上按桌面宽缩放 |
| 手势 | 交互元素加 `touch-action: manipulation` | 去掉 300ms 点击延迟与双击缩放误触 |
| 安全区 | 底栏/顶栏留 `env(safe-area-inset-*)` | 刘海屏、手势条会盖住内容 |
| 热区 | 可点区域 ≥44×44px | 手指命中率 |
| 输入字号 | 输入框 `font-size` ≥16px | 否则 iOS 聚焦时自动放大整页 |
| 双指缩放 | 禁用（`maximum-scale=1, user-scalable=no`）+ **JS 拦 `gesturestart`/`gesturechange`** | iOS Safari 从 10 起忽略 `user-scalable=no`，只写 meta 在 iPhone 上不生效（实测）；有长表格时不要禁 |
| 无构建 | 脚本加载顺序即契约、元素 `id` 即契约 | 没有打包器，顺序与 id 就是接口 |
| 渲染纪律 | 重渲染不许动用户正在输入的节点（输入区/计算区分离） | 全量重绘会把光标、候选栏顶掉 |
| `type=number` 中间态 | `value===''` 且 `validity.badInput` 时直接 `return`，不写回 | 清空/半输入状态会被解析成 NaN 污染数据 |
| 长按 | 允许长按选中文字；图表层长按菜单单独处理 | 别全局 `user-select:none`，用户要能复制数字 |

### 2.3 确认判据：**用户改口才算确认**

- 算数：用户能指出「我要的不是这个，是……」或「少了某某」。
- 不算：用户说「挺好」「不错」「就这样吧」——客气，不是确认。
- 逼出改口：指着具体一块问「这块你们家实际会怎么用？」；用户支吾 = 这块没想清楚。

### 2.4 原型 → 正式版

| 步骤 | 做法 |
| --- | --- |
| 留证 | 原型放 `docs/prototype/` 作证据，别删别覆盖 |
| 重写 | 正式版按契约（接口/字段/id）重写为 `ui/` 三件套（html/css/js） |
| 隔离 | 原型里的假数据**不许**流进正式版；正式版从空的 `<data_dir>` 起 |

### 2.5 原型阶段的禁令

不写后端、不接真实数据、不做鉴权、不承诺性能。以上任何一项在原型阶段动手，都是把未定稿的需求烧进代码。

## 3. 配套 skill 的出货清单

应用能跑 ≠ 交付完成。交付 = 应用 + 一个能让下个 Agent 接手改的 skill。

### 3.1 SKILL.md 必含

| 段 | 内容 |
| --- | --- |
| 触发条件 | description 里一句「Use when……」，明确何时该用它 |
| 命令表 | 每个写操作一个子命令（增/改/删/导入各一条），附示例与副作用 |
| 口径声明 | 关键指标怎么算（含边界：空值、负数、跨期怎么处理） |
| 数据血统 | 唯一真相在 `<data_dir>/state.json`，备份策略，谁可写 |
| 排障 | 起不来/端口占用/数据脏 的处置步骤 |
| 变更记录 | 每次改动一行：改了什么、为什么、怎么验收 |

### 3.2 必配「校验自己 SKILL.md」的零依赖测试

frontmatter 不合规的 skill 在多数宿主上**不报错、只是不触发**——静默失效，所以必须自测：

```bash
node --input-type=module -e '
import fs from "node:fs";
const t = fs.readFileSync("SKILL.md","utf8");
const m = t.match(/^---\n([\s\S]*?)\n---/);
if(!m) throw new Error("缺 frontmatter");
const get = k => (m[1].match(new RegExp("^"+k+":\\s*(.+)$","m"))||[])[1];
const name = get("name"), desc = get("description");
if(!name) throw new Error("缺 name");
if(!desc) throw new Error("缺 description");
if(desc.length > 60) throw new Error("description 超 60 字符: "+desc.length);
console.log("ok", name, desc.length);
'
```

要点：**零依赖**（只用 `node` 内建）、**fail 用退出码**、**放进每次改完 SKILL.md 后的固定动作**。

### 3.3 frontmatter 硬约束

| 字段 | 约束 |
| --- | --- |
| `description` | 一句触发语，**上限 60 字符**（超了会被拒或被索引截断，从而不触发） |
| `name` | 与目录名一致；小写、连字符 |
| 首 57 字符 | 必须自成一句可读的触发（前段被截断时仍能命中） |

### 3.4 何时拆成「应用本体 + 操作层补充」两份 skill

| 信号 | 拆法 |
| --- | --- |
| 领域口径（算钱/算账规则）占正文一半以上 | 本体留运行，口径单独成 skill |
| 上游包由别人维护 | 本体跟上游，补充层跟本地 |
| references 超过 5 篇 | 按主题拆，别让单篇 SKILL.md 变目录 |

## 存疑项

- 「禁用双指缩放」在含长表格/大图表的看板上是负收益，具体阈值（多少行才不禁）未实测定型，暂写为「有长表格时不要禁」。
- 「description 上限 60 字符」是多个宿主的常见阈值，不同宿主实现未必一致；以实际宿主文档为准，测试里按 60 卡。
- 第 1.4 节「用户说对=还没问够」是经验判断，非硬规则；对配合度高的用户可能误伤，按实际情况放宽。
